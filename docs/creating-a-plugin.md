# Creating Your Better Auth Plugin

This repository is a starter package. Replace the email-domain allowlist example
with your plugin's behavior while preserving the server, client, and package
boundaries described below.

## Folder layout

```text
src/
├── index.ts          # Public package API
├── server.ts         # Server-side Better Auth plugin factory
├── client.ts         # Optional Better Auth client companion
├── types.ts          # Public options and shared TypeScript types
├── schema.ts         # Database fields contributed by the plugin
├── helpers.ts        # Small shared, framework-independent utilities
└── routes/
    ├── index.ts      # Route barrel exports
    └── config.ts     # Example custom endpoint

tests/
└── index.test.ts     # Unit and Better Auth integration tests
```

Keep plugin-specific code in `src/`. Do not edit `dist/`; it is generated by
`pnpm build`.

## Start by renaming the example

Choose a stable, kebab-case plugin ID, such as `"organization-policy"`. Then
replace the example's `emailDomainAllowlist` names, option types, error codes,
route paths, and user-facing messages throughout `src/` and `tests/`.

Also update these package-level values in `package.json`:

- `name` — the npm package name that consumers will install.
- `description` — what the plugin does.
- `private` — set to `false` only when the package is ready to publish.
- `exports` — retain the root, `./server`, and `./client` entries if you ship
  all three entry points. Add an entry only for a deliberate public API.
- `peerDependencies` — keep Better Auth versions compatible with the APIs you
  use.

Update the package name and examples in `README.md` at the same time so that
the install and import instructions stay accurate.

## Where to implement each part

### `src/types.ts`: options and public types

Define the configuration passed to your server plugin here. Export types that
an application needs to import, such as plugin options or fields added to a
user/session model.

```ts
export interface OrganizationPolicyOptions {
  requireVerifiedDomain?: boolean;
}
```

Keep runtime validation out of this file; types disappear at runtime. Validate
required configuration in the plugin factory or in a dedicated helper.

### `src/server.ts`: server plugin factory

This is the main implementation. Export a factory function that accepts your
options and returns an object satisfying `BetterAuthPlugin`.

```ts
export function organizationPolicy(options: OrganizationPolicyOptions) {
  return {
    id: "organization-policy",
    // schema, hooks, endpoints, init, options, and $ERROR_CODES as needed
  } satisfies BetterAuthPlugin;
}
```

Edit this file when your plugin needs to:

- validate an auth request with `hooks` and `createAuthMiddleware`;
- add an API endpoint through `endpoints`;
- customize database writes with `init()` and `databaseHooks`;
- expose a schema from `src/schema.ts`;
- define typed error codes with `defineErrorCodes` and throw errors with
  `APIError`.

The starter's sign-up hook and user-create database hook intentionally enforce
the same rule. Follow that pattern when a rule must also apply to users created
through flows other than the HTTP endpoint you hook.

Keep the `declare module "@better-auth/core"` registry entry in sync with the
plugin ID and factory name. It lets Better Auth understand your plugin through
its type registry.

### `src/schema.ts`: database additions

Add fields your plugin persists to Better Auth models. The starter adds a
server-controlled field to `user`; `input: false` prevents clients from
supplying it and `returned: true` makes it available in returned user data.

Only include this file in the server plugin's `schema` property when your
plugin needs database storage. After changing it, consumers must run Better
Auth's migration or generation command in their own application. Design new
fields so existing installations can migrate safely—for example, add a nullable
field first and backfill before later making it required.

### `src/routes/`: custom endpoints

Put each endpoint or closely related endpoint group in its own route file.
Create endpoints with `createAuthEndpoint`, export them from
`src/routes/index.ts`, and register them in `server.ts` under `endpoints`.

If an endpoint is used by the browser client, add its path and method to
`client.ts` as well. Avoid returning secrets or configuration that should stay
server-only; the example route exposes allowlisted domains only when explicitly
configured to do so.

### `src/client.ts`: client companion

Create a client plugin when the application needs typed access to one of your
custom endpoints or client-side plugin metadata. Its `id` must exactly match
the server plugin ID, and `$InferServerPlugin` should reference the server
factory's return type.

```ts
export function organizationPolicyClient() {
  return {
    id: "organization-policy",
    $InferServerPlugin: {} as ReturnType<typeof organizationPolicy>,
    pathMethods: {
      "/organization-policy/config": "GET" as const,
    },
  } satisfies BetterAuthClientPlugin;
}
```

If the plugin has no browser-facing behavior, you may omit the client plugin;
then remove the `./client` package export and its build entry deliberately.

### `src/helpers.ts`: small shared logic

Put pure utilities used by more than one server concern here. The current
domain normalization and matching helpers are examples. Keep helpers easy to
test and independent from the Better Auth request lifecycle.

### `src/index.ts`: supported public API

This is what consumers receive from the package root. Export only the factory,
client companion, option types, errors, and helpers you intend to support.
Internal implementation details can stay unexported. Retain explicit exports so
a package API change is obvious during review.

Use `.js` extensions for new relative imports in TypeScript source, as required
by the package's ESM/NodeNext convention.

## Register the plugin in an application

Consumers install the server factory in `betterAuth` and, when provided, the
client companion in `createAuthClient`:

```ts
import { betterAuth } from "better-auth";
import { organizationPolicy } from "your-package";

export const auth = betterAuth({
  plugins: [organizationPolicy({ requireVerifiedDomain: true })],
});
```

```ts
import { createAuthClient } from "better-auth/client";
import { organizationPolicyClient } from "your-package/client";

export const authClient = createAuthClient({
  plugins: [organizationPolicyClient()],
});
```

Document the plugin's options, database effects, endpoints, errors, and any
required migration in `README.md`.

## Tests and checks

Add or replace tests in `tests/` for every behavior change. Cover at least:

- valid and rejected configuration or requests;
- schema shape and server-controlled fields;
- custom endpoint responses and authorization;
- database-hook behavior when the plugin persists data;
- a real Better Auth flow using `memoryAdapter` when hooks affect auth.

Run these before publishing or opening a pull request:

```sh
pnpm check
pnpm publish:check
```

`pnpm check` runs formatting/linting, type checks, tests, and the build.
`pnpm publish:check` additionally validates exports and the package that npm
would receive.
